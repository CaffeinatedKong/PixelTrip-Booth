# API Contracts

Defines what the frontend expects from the backend. These shapes are the shared contract
that both sides build against: the frontend service layer consumes them and the backend
produces them. Frontend and backend are developed in parallel, so this contract is the
integration point. Treat these as agreed shapes; changes must be coordinated across both
teams.

Notes:
- Data persistence runs through Supabase (no Supabase Auth). AI orchestration runs through
  the FastAPI + LangGraph backend. The frontend does not care which is which beyond the
  service interface.
- All shapes below are conceptual (field lists), not implementation code. IDs are UUID
  strings; timestamps are ISO 8601 strings.

## Guest Identity Flow (No Auth)

There is no sign-up / sign-in. Identity is room-scoped: `room + normalized display name →
room member` (see `supabase-architecture.md`).
- Join input: `{ roomCode, displayName }`.
- Join result: `{ room, member, guest, character, travelPreferences }` (shapes below). If a
  member with the same normalized display name (trimmed, case-insensitive) already exists in
  the room, that member is resumed instead of a new one being created. See "HTTP API" for
  the exact requests.
- All ids are generated by the database/backend — the client never creates identity UUIDs.
- The client may cache `roomId`, `memberId`, `guestId`, and `displayName` locally for
  convenience; this is not authentication and there are no tokens, passwords, or auth
  errors.
- Subsequent calls carry the `memberId`, which is self-asserted (guest/demo trust model).
- "User" in the shapes below means this room member.

Shapes:
- Guest: `{ id, displayName, avatarUrl? }`.
- Party room: `{ id, roomCode, name, status: "active" | "finalised" | "cancelled",
  planningStage }`.
- Room member: `{ id, roomId, guestId, displayName, role: "owner" | "member" }`.
  `displayName` is the name as first entered, even when resumed with different casing.
- Character: `{ id, memberId, appearance, spriteKey? }` — `appearance` is a free-form
  object.
- Travel preferences: `{ id, memberId, availableDates, destinations, travelStyle?,
  budget?, interests, activities, hardConstraints }` — list fields are arrays (empty when
  new); `budget` is a number ≥ 0.

## HTTP API (FastAPI)

The backend endpoints the frontend service layer calls. This section is the source of
truth for paths, request bodies, status codes, and errors. The running backend also serves
interactive docs at `{API_BASE_URL}/docs` (generated from the code); if they disagree with
this section, treat it as a bug and fix one side.

Conventions:
- Base URL: `NEXT_PUBLIC_API_BASE_URL` (local default `http://localhost:8000`).
- JSON bodies, camelCase fields, `Content-Type: application/json`.
- No auth headers. Identity comes from the room code + display name (see above).
- Fields marked `?` may be `null` in responses.

### `GET /health`

Liveness check. `200` → `{ "status": "ok" }`.

### `POST /rooms` — create a room

Creates the room, a unique 6-character room code, and the caller as the `owner` member,
with an empty character and preferences, in one transaction.

Request:

```json
{ "name": "Adventure Club Trip", "ownerDisplayName": "Gerald" }
```

- `name`: 1–100 characters, not blank.
- `ownerDisplayName`: 1–50 characters, not blank.

`200` response (same shape for both room endpoints):

```json
{
  "room": { "id": "…", "roomCode": "1HSM6S", "name": "Adventure Club Trip",
            "status": "active", "planningStage": "setup" },
  "member": { "id": "…", "roomId": "…", "guestId": "…",
              "displayName": "Gerald", "role": "owner" },
  "guest": { "id": "…", "displayName": "Gerald", "avatarUrl": null },
  "character": { "id": "…", "memberId": "…", "appearance": {}, "spriteKey": null },
  "travelPreferences": { "id": "…", "memberId": "…", "availableDates": [],
                         "destinations": [], "travelStyle": null, "budget": null,
                         "interests": [], "activities": [], "hardConstraints": [] }
}
```

Errors: `422 VALIDATION_ERROR`, `500 ROOM_CODE_EXHAUSTED`, `503 DATABASE_ERROR`.

### `POST /rooms/{roomCode}/join` — join or resume

- `roomCode`: 4–12 uppercase letters or digits (e.g. `ABC123`). Anything else is rejected
  with `422` before the room is looked up, so uppercase user input first.
- If the room already has a member whose name matches ignoring case and surrounding
  spaces (`"gerald"` matches `"Gerald"`), that member and their records are returned
  unchanged. Otherwise a new `member`-role member is created.

Request:

```json
{ "displayName": "Priya" }
```

- `displayName`: 1–50 characters, not blank.

`200` response: same shape as `POST /rooms`. On resume, `character` and
`travelPreferences` may be `null` if those records do not exist.

Errors: `404 ROOM_NOT_FOUND`, `409 MEMBER_ALREADY_EXISTS` (two people joined with the same
name at the same moment — retrying the join resumes that member), `422 VALIDATION_ERROR`,
`503 DATABASE_ERROR`.

### Errors

Every error response has this body (never FastAPI's default `{ "detail": … }`):

```json
{ "error": { "code": "ROOM_NOT_FOUND", "message": "Room 'ABC123' not found." } }
```

Branch on `code`, not `message`. `message` is safe to log; it is not tuned for display.

| Status | `code` | Meaning |
|---|---|---|
| 404 | `ROOM_NOT_FOUND` | No room with that code. |
| 409 | `MEMBER_ALREADY_EXISTS` | Name taken in a race; retry the join. |
| 422 | `VALIDATION_ERROR` | Bad body or path; `message` names the fields. |
| 422 | `INVALID_DISPLAY_NAME` | Display name is blank. |
| 500 | `ROOM_CODE_EXHAUSTED` | Could not find a free room code; retry. |
| 500 | `INTERNAL_ERROR` | Unexpected server error. |
| 503 | `DATABASE_ERROR` | Database unavailable or failed; retry later. |

## Chat Message Flow

A room message has a stable envelope:
- `id`, `roomId`, `createdAt`
- `senderType`: `"user" | "ai"`
- `senderId`: room member id (`room_members.id`), or null for AI
- `kind`: `"text" | "recommendation" | "vote" | "summary"`
- `content`: shape depends on `kind` (see below)

Flow:
1. User sends a text message → persisted to Supabase → broadcast via Realtime.
2. Backend AI produces messages (any `kind`) → persisted → broadcast via Realtime.
3. Clients render new messages from the Realtime stream.

## AI Response Structure

An AI turn returns one or more messages sharing the envelope above. Common fields in
`content` for AI text:
- `text`: NPC dialogue string.
- `options?`: array of `{ id, label }` for quick single-choice replies.
- `stage?`: current planning stage indicator (drives progress UI).

## Recommendation Response Structure

`kind: "recommendation"` content. Used in DISCOVER (destinations) and LOGISTICS (flights):
- `title`: short heading.
- `category?`: `"destination" | "flight"` — which stage this set belongs to.
- `items`: array of recommendation entries, each:
  - `id`, `title`, `description`
  - `imageUrl?` / `spriteKey?`
  - `meta?`: key/value details for comparison (e.g. price band, duration, tags).
    For flights this carries the comparable fields (price, airline, duration, stops,
    depart/return times); for destinations, things like region, budget band, highlights.
- `prompt?`: optional follow-up question for the party.

The frontend renders destination and flight option sets with the same recommendation +
comparison UI, keyed off `category`.

## Voting Structure

Voting has a session plus per-member votes.

Vote session (`kind: "vote"` content or dedicated object):
- `voteSessionId`, `roomId`, `question`
- `options`: array of `{ id, label, count }`
- `status`: `"open" | "closed"`

Cast a vote:
- Input: `{ voteSessionId, optionId, memberId }`.
- One vote per member per session; re-voting replaces the previous choice.
- Live counts update via Realtime.

When a vote resolves, the locked choice is stored as a selection
(`{ roomId, kind: "destination" | "flight", data, voteSessionId? }`), one per kind per room.
AI outputs are proposals; the party's decision determines the selection.

## Itinerary Format

The trip plan (rendered as quest log in BUILD/REFINE and adventure summary in WRAP). An
itinerary object:
- `tripId`, `roomId`, `title`, `summary`
- `destination`: `{ name, country? }`
- `dates?`: `{ start, end }`
- `days`: array of day plans, each:
  - `day`: number
  - `date?`
  - `items`: ordered activities, each `{ id, time?, title, description?, location?, tags? }`.
    `id` is stable across versions so feedback can target a specific activity.
- `map?`: points array `{ label, lat, lng }` for the travel map view.

The journal, quest log, timeline, and map are all derived from this single object.

## Itinerary Versioning

BUILD produces version 1; REFINE appends new versions (history is never overwritten). A
version wraps the itinerary:
- `id`: itinerary version id.
- `version`: incrementing integer, unique per trip.
- `source`: `"build" | "refine"`.
- `status`: `"proposed" | "approved" | "rejected" | "superseded"`.
- `itinerary`: the itinerary object above.
- `changeSummary?`: short note of what changed vs. the prior version (REFINE only).

The UI can list versions and step through/compare them. At most one version per trip is
`approved`; the version under review is the latest `proposed` one.

## Feedback & Refinement (REFINE)

Feedback entry (submitted by a party member):
- Input: `{ tripId, itineraryVersionId, memberId, target, comment }`
  - `target`: structured reference to what the feedback applies to, e.g.
    `{ day?, itemId?, section? }`.
  - `comment`: the party member's comment or suggested change.
- `status`: `"open" | "addressed"`.

Refinement result (from the AI):
- An analysis `text`/`summary` message: conflicts identified and compromises proposed.
- A new itinerary version (see above) with `source: "refine"`, `status: "proposed"`, and a
  `changeSummary`. The version it replaces becomes `superseded`.
- Decision: `{ tripId, itineraryVersionId, decision: "approve" | "reject" }`. Approving
  marks the version `approved` and advances toward WRAP.

## AI Runs

Each AI operation (discovery, logistics, itinerary, refinement) is tracked as a run:
- `{ id, tripId, runType, status, baseVersion, resultVersionId?, error? }`
  - `runType`: `"discovery" | "logistics" | "itinerary" | "refinement"`.
  - `status`: `"pending" | "running" | "completed" | "failed"`.
  - `baseVersion`: the itinerary version number the run started from (0 = none yet).
- Requests that trigger a run may send an `idempotencyKey`; repeating a request with the
  same key returns the existing run instead of starting a duplicate.

## Stage & State

Every planning surface reflects where the party is:
- `stage`: `"setup" | "discover" | "logistics" | "build" | "refine" | "wrap"` — the active
  stage (also carried on AI `text` content).
- `state`: the application-state progression (see `system-workflow.md`) that gates
  transitions and drives progress UI. Stored as the trip status, one of:
  `"trip_created" | "group_formed" | "preferences_collected" | "destination_selected" |
  "flight_selected" | "itinerary_generated" | "feedback_collected" |
  "refinement_completed" | "trip_approved" | "trip_exported"`.

## Export (WRAP)

Finalisation returns:
- The approved itinerary version.
- `export`: a shareable payload the WRAP UI offers to share/download.
